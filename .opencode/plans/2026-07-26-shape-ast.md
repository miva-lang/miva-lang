# ADR-002: Shape AST Representation

**Status:** Proposed  
**Date:** 2026-07-26

## Context

Miva's type system is represented through the `Typ` enum and definitions through the `Def` enum in `miva/src/ast.rs`. Adding shapes requires extending both.

## Decision

### New `Def` variant: `DShape`

```rust
#[serde(rename = "shape")]
DShape {
    loc: Loc,
    name: String,
    fields: Vec<FieldDef>,
    #[serde(default)]
    type_params: Vec<String>,
},
```

Structurally identical to `DStruct` but with a different serde tag. Fields use the same `FieldDef { name, typ }` structure.

### New `Typ` variant: `TShape`

```rust
#[serde(rename = "shape")]
TShape {
    name: String,
},
```

Used when a shape is referenced as a type (in annotations, bounds, etc.). Similar to how `TStruct` represents struct types but without inline field data — the shape's fields are looked up from the shape registry.

### No changes to frontend AST

The frontend (`miva-frontend-rs/src/ast.rs`) must mirror these changes exactly since the compiler receives its input as JSON from the frontend. Both AST files must stay in sync.

## Rationale

- Keeping `DShape` parallel to `DStruct` minimizes cognitive load and code duplication
- `TShape` is simpler than `TStruct` because it only carries a name — field data comes from the shape registry, not from the type itself
- The serde rename tag `"shape"` distinguishes it from `"struct"` in the JSON AST
