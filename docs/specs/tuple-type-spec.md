# Miva 元组类型（Tuple Type）规范

## 问题陈述

Miva 当前缺乏复合值打包能力。开发者需要将多个相关值组合传递时，只能使用命名结构体（struct），这引入了不必要的类型定义开销和命名负担。例如，交换两个值的函数需要：

```miva
struct SwapPair {
    a: int,
    b: int,
}

swap = (p: SwapPair): SwapPair => { ... }
```

用户需要一个轻量级的、无需命名声明的复合值类型，即元组。

## 解决方案

为 Miva 语言添加原生元组类型支持，包括：
- **类型语法**：`(int, bool, string)` 在类型位置使用
- **字面量语法**：`(1, true, "hello")` 在表达式位置使用
- **字段访问**：`t.0`、`t.1` 数字索引访问
- **解构绑定**：`let (a, b) = t` 支持嵌套解构

元组类型通过新增 `Typ::TTuple` 变体实现，而非合成结构体，以保持类型系统的完整性和可推理性。

## 用户故事

1. 作为 Miva 开发者，我希望使用 `(int, bool)` 这样的语法声明元组类型，这样我就不需要为简单的值对定义命名结构体。

2. 作为 Miva 开发者，我希望编写 `let pair = (1, true)` 来创建元组字面量，这样我就可以快速构造复合值。

3. 作为 Miva 开发者，我希望通过 `pair.0` 和 `pair.1` 访问元组元素，这样我可以使用位置索引获取元素值。

4. 作为 Miva 开发者，我希望使用 `let (a, b) = pair` 进行元组解构，这样我可以直接将元组元素绑定到命名变量。

5. 作为 Miva 开发者，我希望支持嵌套元组解构 `let ((a, b), c) = nested`，这样我可以处理多层嵌套的复合数据结构。

6. 作为 Miva 开发者，我希望元组可以作为函数参数类型使用，这样我可以用 `(int, int)` 接收多个值。

7. 作为 Miva 开发者，我希望元组可以作为函数返回值类型使用，这样我可以从函数返回多个值。

8. 作为 Miva 开发者，我希望 `let (a, b): (int, bool) = pair` 支持显式类型注解的解构，这样我可以在解构时明确指定类型。

9. 作为 Miva 开发者，我希望 `let (a, b) = pair` 在没有类型注解时自动从表达式类型推断元素类型，这样我可以编写更简洁的代码。

10. 作为 Miva 开发者，我希望元组支持 `==` 和 `!=` 比较操作，这样我可以检查两个元组是否相等。

11. 作为 Miva 开发者，我希望当元组包含 droppable 类型元素时，编译器自动插入 drop glue，这样我的资源管理是确定性的。

12. 作为 Miva 开发者，我希望元组的 droppable 属性递归传播，即任意元素 droppable 则整个元组 droppable，这样我无需手动跟踪资源生命周期。

13. 作为 Miva 开发者，我希望当元组 move 时，所有元素都被 move，这样所有权语义保持一致。

14. 作为 Miva 开发者，我希望元组在 cxx、llvm、mvm 三个后端都有正确实现，这样我可以选择任意后端编译运行。

15. 作为 Miva 开发者，我希望跨后端的一致性保证，即同一程序在三个后端输出相同结果，这样我可以在不同后端间切换而无差异。

16. 作为 Miva 开发者，我希望单元素元组 `(int)` 被拒绝并报错误，这样我避免意外的语法歧义。

17. 作为 Miva 开发者，我希望空元组 `()` 被视为 unit 类型（TNull），这样我可以复用现有 unit 语义。

18. 作为 Miva 开发者，我希望元组类型可以在类型注解位置使用，如 `x: (int, bool)`，这样我可以显式标注变量类型。

19. 作为 Miva 开发者，我希望在 `choose` 表达式中不使用元组解构（保持简单），这样我不增加模式匹配的复杂度。

20. 作为 Miva 开发者，我希望元组元素类型不一致时报类型错误，这样我可以在编译期捕获错误。

## 实现决策

### 类型系统

元组类型通过 `Typ` 枚举新增 `TTuple { elems: Vec<Typ> }` 变体实现。这使元组类型在类型系统中是一等公民，支持：
- 类型相等比较（`types_equal`）
- Droppable 传播分析
- 泛型参数 ban 检查
- 跨模块引用（虽然元组通常是匿名的）

### 语法设计

- **类型位置**：`(t1, t2, ...)` 逗号分隔的类型列表，括号内
- **表达式位置**：`(e1, e2, ...)` 逗号分隔的表达式列表，括号内
- **字段访问**：`expr.0`、`expr.1` 等数字索引
- **解构语法**：`let (pat1, pat2) = expr`，支持嵌套 `(a, (b, c))`

### 与 Lambda 的歧义消解

解析器已有 `is_lambda_head` 预测性检查用于区分 lambda `(x: int): ret =>` 和分组表达式 `(expr)`。新增规则：当 `(` 后跟随非 `ident:` 模式（如字面量、嵌套括号）时，解析为元组。

### 语义分析

- `ETupleLit` 递归检查所有元素表达式的 move 状态
- TTuple 的 droppable 检查递归到每个元素
- 解构绑定时递归注册每个绑定变量的类型

### Drop 管理

编译器为含 droppable 元素的元组生成 drop glue，按元素顺序左到右 drop。元组本身无 `op_drop` 实现，drop 由编译器合成。

### 三个后端实现

| 后端 | 元组表示 | 创建 | 访问 |
|------|----------|------|------|
| CXX | `std::tuple<T1, T2, ...>` | `std::make_tuple(...)` | `std::get<N>(...)` |
| LLVM | `%{i64, i64, ...}` | alloca + store 各元素 | gep + load |
| MVM | 复用 StructNew/StructGet | PushStruct（复用） | StructGet |

## 测试决策

### 测试策略

采用 **tests-after** 策略，在实现完成后添加测试。测试聚焦于外部行为：

1. **前端解析测试**：验证元组类型/字面量的正确解析
2. **语义分析测试**：验证 move 检查和 droppable 传播
3. **类型检查测试**：验证类型推断和解构绑定
4. **后端一致性测试**：验证三个后端输出相同
5. **Drop 行为测试**：验证资源正确释放

### 测试模块

- `miva-frontend-rs`: 解析器单元测试
- `miva/src/semantic/tests`: 语义分析测试
- `miva/src/typecheck/tests`: 类型检查测试
- `miva/src/codegen/cxx_ir/tests`: CXX IR 测试
- `miva/src/codegen/llvm/tests`: LLVM IR 测试
- `miva/tests/backend_parity.rs`: 后端一致性集成测试

### 测试先例

参考现有的结构体/枚举测试模式：
- `test_all_type_variants` 在 `miva/src/json_ast.rs` 中测试所有类型变体
- `backend_parity.rs` 中已有 struct/enum 测试用于三后端一致性验证

## 超出范围

- **单元素元组**：`(int)` 不被支持，报 E0016 错误
- **choose 中的元组解构**：不在 v1 中支持，保持模式匹配简单
- **函数参数解构**：`fn foo((a, b): (int, int))` 语法不支持
- **元组 clone**：无 clone trait 系统，不支持
- **元组作为泛型参数**：沿用 E0036 droppable 检查，droppable 元组不可作泛型参数
- **元组比较运算符**：仅支持 `==` 和 `!=`，不支持 `<`、`>` 等
- **空元组独立类型**：`()` 映射到现有 `TNull`（unit），不引入新类型
- **元组作为 shape 约束**：不在 v1 中支持

## 进一步说明

### 向后兼容性

此改动向后兼容，不修改现有类型系统行为。新增的 `TTuple` 和 `ETupleLit` 是纯扩展。

### 性能考量

- CXX 后端：`std::tuple` 是零开销抽象，编译期展开
- LLVM 后端：tuple 类型直接映射到 LLVM struct type
- MVM 后端：复用 struct 操作码，无额外运行时开销

### 错误消息

新增以下错误码：
- E0016：单元素元组不被支持
- E0014：元组类型不匹配

### 代码生成模式

元组在代码生成中遵循与结构体相同的模式：
1. 创建时按元素顺序 push/存储
2. 访问时按索引 load/检索
3. Drop 时按元素顺序左到右清理
